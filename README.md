# topwords

Параллельный CLI-подсчёт топ-N самых частых слов длиной больше заданной в каталоге текстовых файлов. Реализация на Go 1.26.1 без сторонних рантайм-зависимостей; токенизация - через `regexp` (Unicode-классы), отмена - через `context.Context`.
Припроектировании учитыввалились принципы SOLID.
## Установка / запуск

```bash
go run ./cmd/topwords --dir ./testdata/corpus
```

Сборка bin файла:

```bash
go build -o bin/topwords ./cmd/topwords
./bin/topwords --dir ./testdata/corpus
```

В `testdata/` лежат две папки фикстур:

- `testdata/corpus/` — основной корпус для smoke-теста: только обычные текстовые файлы.
- `testdata/mixed/` — edge-кейсы: текст с числами, два бинарных файла (с NUL-байтами и ASCII-«псевдо-словами»). Используется для ручной проверки, что числа не попадают в результат, а бинарные файлы пропускаются. Подробнее — в `testdata/mixed/README.md`.

## Флаги

| Флаг            | По умолчанию       | Описание                                                                |
| --------------- | ------------------ | ----------------------------------------------------------------------- |
| `--dir`         | (обязательный)     | Каталог с текстовыми файлами (рекурсивно, без следования по симлинкам). |
| `--min-length`  | `4`                | Учитываются слова, длина которых СТРОГО больше значения (в кодпойнтах). |
| `--top`         | `10`               | Сколько слов выводить.                                                  |
| `--workers`     | `runtime.NumCPU()` | Количество параллельных воркеров.                                       |
| `--format`      | `text`             | Формат вывода: `text` или `json`.                                       |
| `--log-level`   | `info`             | Уровень логов в `stderr`: `debug`/`info`/`warn`/`error`.                |

## Форматы вывода

`text` (`stdout`, по строке на слово):

```
1<TAB>brown<TAB>8
2<TAB>hello<TAB>4
```

`json` (`stdout`, JSON-массив):

```json
[
  { "rank": 1, "word": "brown", "count": 8 },
  { "rank": 2, "word": "hello", "count": 4 }
]
```

При равной частоте слова сортируются лексикографически по возрастанию - порядок детерминирован.

## Коды возврата

| Код | Случай                                                          |
| --- | --------------------------------------------------------------- |
| 0   | Успех (включая запуск с `--help`).                              |
| 1   | Ошибка обработки (например, ни один файл не прочитан успешно).  |
| 2   | Ошибка использования: невалидные флаги, отсутствие/тип `--dir`. |
| 130 | Прерван SIGINT/SIGTERM.                                         |

## Что считается «словом» и «текстовым файлом»

**Регекс:** `\p{L}[\p{L}\p{N}'\-]*[\p{L}\p{N}]|\p{L}` - слово ОБЯЗАНО начинаться с Unicode-буквы, может содержать буквы/цифры/дефис/апостроф внутри, заканчивается буквой или цифрой (либо это одиночная буква).

| Вход | Считается? | Почему |
|------|-----------|--------|
| `Hello`, `мир` | ✓ | обычные слова |
| `well-known`, `it's` | ✓ | дефис/апостроф внутри |
| `H2O`, `mp3`, `ipv4` | ✓ | начинается буквой, цифры допустимы |
| `2024`, `42` | ✗ | чистое число - не слово по смыслу ТЗ |
| `_foo`, `--bar` | ✗ | не начинается с буквы |

Токены нормализуются к нижнему регистру (`strings.ToLower`); фильтр `min-length` применяется к длине в кодпойнтах (`utf8.RuneCount`), не байтах.

**Текстовые vs бинарные файлы.** Перед обработкой каждый файл «нюхается» по первым 4 КиБ:
- если есть NUL-байт - бинарь, файл пропускается;
- если содержимое не валидный UTF-8 (с допуском 3 байт на оборванную руну в хвосте) - бинарь, пропускается;
- иначе - текст, обрабатывается.

Пропущенные файлы не считаются ошибкой и логируются на уровне `info`. Итоговый Result содержит счётчики `Processed`/`Skipped`/`Failed`.

### Что считается «текстовым» — явные ограничения

Под «текстовым файлом» утилита понимает **UTF-8 (включая ASCII как подмножество) без NUL-байтов**. Это сознательное упрощение:

- **UTF-16 LE/BE с BOM** — пропускаются как non-text (BOM `0xFF 0xFE` / `0xFE 0xFF` + чередующиеся NUL-байты в ASCII-тексте → срабатывает NUL-фильтр).
- **Windows-1251, KOI8-R и другие 8-битные legacy кодировки** — пропускаются как не валидный UTF-8 (любой высокий байт без правильной continuation-последовательности).
- **UTF-8 с BOM (`EF BB BF`)** — обрабатывается, BOM просто не матчится регэкспом.

Поддержку UTF-16/legacy можно добавить через `golang.org/x/text/encoding` + BOM-detection, но это **внешняя зависимость и +код**. Для Windows-проекта, где CP1251-файлы реальны, это разумная следующая итерация — но в текущей задаче мы остановились на UTF-8 как на 80% покрытия типичных корпусов.

**Фильтр по расширению намеренно не применяется.** Утилита смотрит на содержимое, а не на имя файла:

- `.md`, `.log`, `.csv`, `.json` без NUL-байтов будут обработаны — что обычно полезно (`README.md` в testdata/mixed обрабатывается, и это видно в smoke-выдаче).
- `.txt` с BOM-UTF-16 — будет пропущен (см. выше).

Если ревьюер ожидает «только `.txt`» — это одна строка кода (`if filepath.Ext(p) != ".txt" { return nil }` в scanner) и один флаг. Я не добавил, потому что content-based sniff более универсален и ТЗ не уточняет.

## Конкурентная схема

```
producer (Walker) -- paths(chan) -> workers (K) -- partials(chan) -> aggregator
                                         │
                                         └── читают файл, токенизируют, копят локальный map[string]int
```

`paths` закрывает producer (по завершении обхода или отмене ctx); `partials` закрывает координатор после `WaitGroup.Wait()` всех воркеров. Агрегатор - единственный получатель `partials`, поэтому общий счётчик не требует мьютекса.

## Соответствие ТЗ vs авторские расширения

ТЗ дословно: *«приложение, которое выдаёт список из 10 самых часто используемых слов, длина которых превышает заданную; подсчёт в множестве текстовых файлов в указанной папке; в многопоточном режиме; для анализа слов использовать Regex»*.

**Что сделано буквально по ТЗ:**

| Пункт ТЗ | Реализация |
|----------|------------|
| Топ-10 слов | Параметр `--top` со значением по умолчанию `10`. |
| Длина больше заданной | Параметр `--min-length` (фильтр по `utf8.RuneCount > MinLength`). |
| Множество текстовых файлов в папке | Рекурсивный обход + sniff на «текстовость». |
| Многопоточный режим | Worker-пул goroutine'ов, координация через каналы. |
| Использовать Regex | `regexp.MustCompile(\p{L}...)` - ровно один шаблон, без альтернативных режимов. |

**Авторские расширения (за пределами буквы ТЗ):**

| Расширение | Зачем добавил |
|------------|---------------|
| `--top N` (вместо фиксированных 10) | Чаще полезно, реализуется одной строкой. Дефолт = 10 как в ТЗ. |
| `--min-length` (вместо хардкода) | ТЗ говорит «длина превышает заданную» - заданная **где** не указано, флаг - самый идиоматичный канал. |
| `--workers` | По умолчанию `runtime.NumCPU()`. Полезно для бенчей и тюнинга. |
| `--format text|json` | `text` - дефолт по ТЗ-стилю; `json` - для интеграции в pipeline. |
| `--log-level` | Стандартная гигиена для CLI на Go. |
| Рекурсивный обход подкаталогов | ТЗ говорит «в указанной папке» без явного «только верхний уровень». Рекурсия - более ожидаемое поведение для CLI; не-рекурсивный режим можно добавить флагом, если нужно. |
| Sniff на «текстовость» (NUL/UTF-8) | ТЗ говорит «текстовых файлов» - без фильтра бинарные файлы засоряли бы результат байтами, читающимися как ASCII-«слова». |
| Skipped/Failed в Result | Помогает диагностике, не меняет основной контракт. |
| Goroutines вместо OS-threads | ТЗ упоминает «реализация на Thread». В Go нет POSIX-threads как примитива, концептуальный аналог - goroutine + channel. Прямое использование `runtime.LockOSThread` ничего не дало бы; идиоматичный путь именно goroutines. Если ревьюер требует буквальное соответствие - это место для дискуссии. |

## Структура пакетов

```
cmd/topwords/        точка входа: парсит флаги, собирает зависимости, склеивает adapter'ы
internal/config/     парсинг и валидация флагов, фабрика логгера
internal/output/     EntryWriter + реализации (TextWriter, JSONWriter) + WriterFor
internal/counter/    оркестрация: Counter с интерфейсами Walker и fileTokenizer
internal/scanner/    обход дерева через filepath.WalkDir
internal/tokenizer/  потоковый Regex-токенизатор + фильтр длины
internal/topk/       выбор N самых частых через container/heap
```

Зависимости: `cmd - config, output, counter, scanner, tokenizer, topk` · `config - output` · `counter - (только инерфейсы)`: остальные - листья без внутренних зависимостей.

## SOLID

Принципы применялись там, где они снижают стоимость изменений или улучшают тестируемость, и сознательно НЕ применялись там, где дали бы только лишние абстракции.

### S - Single Responsibility

**Применено.** Каждый пакет - одна ответственность:
- `config` - какие у нас параметры
- `output` - как сериализовать результат
- `counter` -как параллельно посчитать
- `scanner`, `tokenizer`, `topk` - каждый по одной задаче

`Counter.Run` декомпозирован на `validate`, `startProducer`, `startWorkers`, `aggregate`, `processFile` - каждый метод можно прочитать и проверить отдельно.

**Не применено** к разделению `BuildLogger` и `ParseFlags`. Оба живут в `config`, потому что обе функции работают со строковыми именами уровней/флагов и на двоих помещаются в один экранный пакет (~120 строк). Разносить ради SRP в отдельный `logging`-пакет - лишняя поверхность импорта при нулевой выгоде.

### O - Open/Closed

**Применено.** Форматы вывода расширяются без правки `main`:

```go
type EntryWriter interface {
    Write(w io.Writer, entries []topk.Entry) error
}

func WriterFor(f Format) (EntryWriter, error) { /* switch text|json */ }
```

Добавить YAML/CSV/таблицу - это новый тип + одна ветка в `WriterFor`, вызывающий код в `main.go` не меняется (`writer.Write(stdout, entries)`).

**Не применено** к регулярному выражению токенизатора. `wordRE` скомпилирован один раз через `regexp.MustCompile` на уровне пакета. Менять правила токенизации - это, по сути, менять контракт "что считается словом" в этом проекте; делать его точкой расширения через инжекцию `*regexp.Regexp` означало бы дать пользователю ломать инварианты тестов и спецификации. ТЗ фиксирует подход "через Regex", без вариаций.

### L - Liskov Substitution

**Применено.** `fileTokenizer` и `Walker` - узкие интерфейсы; в тестах реальные реализации заменяются на `flakyTokenizer`, `alwaysFailTokenizer`, `listWalker`, `scanWalker` без изменения контракта потребителя - все ведут себя одинаково с точки зрения `Counter`.

### I - Interface Segregation

**Применено.** Интерфейсы - ровно по одному методу:
- `fileTokenizer.Tokenize`,
- `Walker.Walk`,
- `EntryWriter.Write`.

Каждый клиент видит только то, что ему нужно.

**Не применено** к `*slog.Logger`: `Counter.Logger` принимает конкретный тип. Можно было бы определить узкий интерфейс с `Warn`/`Debug`, но `*slog.Logger` - стандартизированное API из stdlib (Go 1.21+); строить вокруг него ещё один интерфейс ради гипотетической подмены - это абстракция ради абстракции. В тестах используется `slog.New(slog.NewTextHandler(io.Discard, ...))` - это нормальный способ заглушить логгер.

### D - Dependency Inversion

**Применено.** Высокоуровневый `Counter` зависит только от интерфейсов:
- `fileTokenizer` (объявлен на стороне consumer'а - каноничный Go-паттерн);
- `Walker` (объявлен в `counter`, реализуется в `cmd/topwords` через `fsWalker`-адаптер вокруг `scanner.Walk`).

`Counter` НЕ импортирует `scanner` и `tokenizer`. Это видно в `import` блоке `internal/counter/counter.go` - только stdlib.

**Не применено** к `os.Open` внутри `processFile`. Можно было бы инжектить `fs.FS` или `func(string) (io.ReadCloser, error)`, но `scanner.Walk` строится на `filepath.WalkDir` (а не `fs.FS`), и инжектить только половину абстракции - путь к расхождениям. Тесты работают через `t.TempDir()`, реальной потребности в моке файловых открытий нет.

## Performance

### Что я смотрел при оценке эффективности

1. **Throughput (МБ/с)** - `BenchmarkTokenize_1MiB` и `BenchmarkRun_Workers` с `b.SetBytes(...)`, чтобы Go выводил MB/s в стандартном виде.
2. **Allocations / GC pressure** - `b.ReportAllocs()` на горячих путях; цель - минимум аллокаций на токен.
3. **Scaling по воркерам** - sub-benchmark по `workers=1,2,4,8,NumCPU`. Если scaling плоский - где-то лок или single-threaded bottleneck.
4. **Memory footprint** - счётчик хранит только уникальные слова; стриминг чтения, никаких `io.ReadAll`.
5. **I/O** - sequential reads через chunked reader (64 КиБ блоки); один `Seek` на старте файла после sniff'а, никаких повторных `Open`.
6. **Algorithmic complexity** - top-N через мин-кучу O(M log N), агрегация без мьютексов.

### Оптимизации заранее

- **Регэксп компилируется один раз** через `regexp.MustCompile` на уровне пакета, а не на файл/строку.
- **Локальные `map[string]int` на воркер** + **единственный получатель `partials`** - нулевая контеншн на горячем пути подсчёта.
- **`paths`-канал буферизирован на `Workers`** - producer не упирается в один-в-один rendezvous с воркерами.
- **Min-heap для top-N**: не сортируем всю карту O(M log M), берём ровно N лучших за O(M log N).
- **Фильтр по длине применяется на `[]byte` ДО `string(...)`** в токенизаторе - токены, которые мы всё равно отбросим, не аллоцируют строку.
- **`*os.File` напрямую в токенизатор** - без обёртки `bufio.NewReader`, потому что токенизатор сам владеет своим chunk-буфером.
- **`FindAllIndex` вместо `FindAll`** - отдаёт позиции, не копирует подстроки. На исходной построчной реализации это сняло ~18% аллокаций.
- **`utf8.RuneCount` для длины** - корректно для многобайтовых символов, без conversion to string.
- **Chunked reader без понятия «строки»** - валидный текстовый файл с одной длинной строкой обрабатывается полностью, токен, разрезанный границей chunk а, собирается через carry-буфер. Защита от patological roста carry: `MaxTokenSize` (1 МиБ) - при превышении токен эмитится без склейки.
- **Sniff на текстовость на первых 4 КиБ** - предотвращает «загрязнение» результата случайными байтами из бинарных файлов, цена - один `Seek(0)` после sniff а.
- **Cancellation между chunk'ами** - длинные файлы не задерживают завершение по SIGINT дольше, чем чтение одного chunk а (≤ 64 КиБ).

### Замеренные цифры (Ryzen 9 9950X3D, Windows; цифры зависят от железа и нагрузки)

Воспроизводимая команда - в разделе [Проверки](#проверки) ниже. Фактические значения на ваше железо могут отличаться, важны порядки и характер scaling.

`BenchmarkTokenize_1MiB` (один поток, текст с переводами строк, min-length=3):

| Метрика     | Значение      |
| ----------- | ------------- |
| ns/op       | ~44 000 000   |
| MB/s        | ~24           |
| B/op        | ~20 МБ        |
| allocs/op   | ~245 000      |

Chunked reader дороже исходной построчной реализации (~26 ms → ~44 ms), но снимает жёсткий лимит на длину строки и обрабатывает файлы без `\n`. Это сознательный trade-off в пользу корректности.

`BenchmarkRun_Workers` (полный пайплайн, 64 файла × ~12 КиБ):

| Workers   | MB/s    | Speedup  |
| --------- | ------- | -------- |
| 1         | 25      | 1.0x     |
| 2         | 33      | 1.3x     |
| 4         | 50      | 2.0x     |
| 8         | 69      | 2.8x     |
| NumCPU=32 | 130     | **5.2x** |

Scaling сублинейный (Amdahl): producer, finalize и регекс-машина на каждом воркере держат serial-fraction. Но многопоточный режим даёт реальное ускорение на CPU-bound нагрузке.

### Что обоснованно НЕ реализовано - оставлено как осознанное предположение

| Идея | Почему не сделал                                                                                                                                                                                                 |
|------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **`sync.Pool` для буферов scanner и локальных карт** | Жизненный цикл буферов прост (один buffer на файл); pool дал бы мизерный выигрыш ценой усложнения.                                                                                                               |
| **Ручной (не-regex) токенизатор** через `bufio.Reader.ReadRune` + `unicode.IsLetter` | Был бы в 3–5× быстрее, но **ТЗ явно требует Regex**. Менять ТЗ нелья =)                                                                                                                                          |
| **Параллельное чтение одного большого файла** (chunk + offsets) | ТЗ говорит "множество текстовых файлов в папке" -> параллелизм по файлам. Если корпус - один гигантский файл, нужен другой паттерн (mmap + chunked scan по `\n`-границам). Делать оба без указаний вТЗ - оверкилл. |
| **Streaming-агрегация** (Count-min sketch / HyperLogLog) | Это для сценария "не помещается в память""; типичный естественный язык даёт сотни тысяч уникальных слов, что свободно умещается. Точность важнее экономии памяти для CLI-утилиты.                                  |
| **Pipelined аггрегатор** (несколько aggregator-goroutine'ов с шардированием) | Сейчас единственный агрегатор сводит K локальных карт за O(уникальных слов в K картах). На наших объёмах он не на критическом пути; шардирование добавило бы сложности.                                          |
| **`fs.FS`-абстракция для I/O** | `filepath.WalkDir` не использует `fs.FS`, и инжектить только половину абстракции - путь к расхождениям. Тесты через `t.TempDir()` покрывают потребности.                                                         |
| **Адаптивный размер пула** (детектировать I/O- vs CPU-bound) | По умолчанию `runtime.NumCPU()` + флаг `--workers` для ручного тюнинга. Auto-tuning в CLI-утилите - оверинжиниринг.                                                                                              |
| **Lock-free агрегация** через атомарную хеш-таблицу | `sync.Map` не подходит (паттерн "много write" - её anti-use-case), а ручная lock-free хешка - большой код ради единиц процентов. Локальные карты + слияние в конце дают тот же эффект проще.                     |
